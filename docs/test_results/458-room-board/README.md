# 운영자 숙소 화면 (G3 #458)·다시 볼 것 (A11 #461) 확인 기록

2026-11-25. 로컬 서버(백엔드 `local` 프로파일, PostgreSQL 17 Docker) + 프런트 `pnpm dev`(mock 끔, 실제 API), Playwright Chromium. 작업 브랜치 `claude/g3-room-board`.

준비(`setup.py`): API로 새 행사(ACTIVE, 2027-01-22–24 두 밤), SQL로 신청서 질문(성별·참석·숙박 밤·숙박 안 함)과 **가상 참가자 200명**의 제출 신청. 숙박 187명, 숙박 안 함 13명(집회만 10, "숙박 안 함" 체크 3), 성별 답 없음 8명(일부는 숙박 안 함). 조 20개(10명씩)를 API로 짜서 공개했다. 클릭은 OWNER(Local owner).

## 막힌 점·알게 된 점

- 첫 실행에서 "보이는 사람 모두 고르기"가 숙박 안 함 13명까지 골라, 보낼 때 "13명은 뺐어요"가 나왔다. 고를 수 있는 사람만 고르도록 고쳤다.
- 정원이 딱 찬 방(6/6)도 빨간 숫자였다. 넘칠 때만 빨갛게 고쳤다.
- 손으로 시드한 신청서 질문에 `minSelect`·`maxLength`가 없어 참가자 수정(`PUT /participant/application`)이 500이었다(`AnswerEvaluator`가 설정 키를 그대로 읽는다). 신청서 만들기 화면을 거친 질문에는 늘 있는 키라 시드를 고쳤다. 서버 코드는 바꾸지 않았다.
- 28번 보내기가 가장 오래 걸린다(한 번에 1.7초 남짓: 보내기 → 배정판 다시 읽기). 방마다 6명씩 고르는 일이 사람 손으로는 더 길다. 조 단위 일괄 배정이나 "보이는 사람 모두 고르기"로 큰 묶음을 넣고 끌어 놓기로 다듬는 편이 빠르다.
- 화면에 조 편성 작업본 기준("작업 중인 조")도 고를 수 있다(GROUP_WRITE가 있을 때). 이번 실행은 공개된 조로 했다.

## 하지 못한 것

- 운영 서버(scene.greengroove.app) 확인, 실제 사람 손으로 잰 시간, 실제 휴대폰에서 손가락 끌기.
- 참가자 숙소 화면(G4)·참가 현황 표·CSV·현장 명단의 방(G5)은 다른 세션 범위다. 알림 187명은 서버 응답 수만 봤다.
- 신청서 칸(참석 칸 막대)이 있는 행사: 이 시드는 식사·집회 칸 질문이 없어 막대가 그려지지 않는다. 칸 막대는 mock 테스트와 조 편성 부품으로 확인했다.
