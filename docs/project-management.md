# SCENE 진행 관리

[GitHub Projects 보드](https://github.com/users/BeomhyunPark/projects/5/views/1)를 진행 상황과 다음 행동의 기준으로 사용한다. README는 프로젝트 소개를 담당하고, 제품·기술 결정의 상세 근거는 해당 문서에 남긴다.

## 작업 기록

작업은 GitHub Issue로 기록하고 Project에 연결한다. 제목은 완료했을 때 무엇이 달라지는지 알 수 있게 작성한다. Issue에는 다음 정보를 남긴다.

- 목적과 현재 상황
- 담당자와 다음 행동
- 사용자가 확인하거나 결정해야 하는 내용
- 완료 조건
- 관련 문서, PR, 커밋과 검증 결과

다음 행동은 “검토하기”처럼 넓게 적지 않고 “참가 신청 취소 시 보관할 정보를 결정한다”처럼 다시 시작할 수 있는 단위로 적는다. 결정 대기는 질문, 선택지, 추천안과 영향을 함께 기록한다.

## 보드 구성

2026-09-30에 확인한 `SCENE Development` 보드의 기존 상태를 사용한다.

| 상태 | 의미 |
| --- | --- |
| Backlog | 필요하지만 아직 시작 순서를 정하지 않은 일 |
| Ready | 목적과 완료 조건이 정리되어 시작할 수 있는 일 |
| In Progress | 실제로 진행 중인 일 |
| Review | 결과가 준비되어 사용자의 검토나 확인을 기다리는 일 |
| Done | 완료 조건을 충족하고 결과 링크를 남긴 일 |

Assignees로 담당자를 표시한다. 검토가 필요한 결과는 Review로 옮기고 Issue 본문에 사용자가 확인할 내용을 적는다. 외부 작업이나 정책 결정 때문에 진행할 수 없다면 Issue에 대기 이유, 해결할 사람과 재개 조건을 기록한다.

보드에서 Ready는 다음 할 일, Review는 검토할 일, Done은 완료 기록으로 확인한다. 우선순위, 목표일이나 별도 뷰는 필요한 시점에 추가한다.

## 작업 시작과 마무리

코드·문서 변경은 작업 브랜치에서 진행한다. 시작 전에 `main`에서 목적에 맞는 브랜치를 만들고, 이미 진행 중인 작업이라면 해당 브랜치를 사용한다. `main`에 직접 커밋·푸시하지 않는다. 검토 가능한 단위로 커밋하고 작업 브랜치를 푸시한 뒤 PR로 변경을 검토한다.

큰 작업은 상위 이슈 하나와 세부 하위 이슈로 나눠 프로젝트에 등록한다. 작업 범위 안의 이슈 생성·등록·상태 갱신은 별도 확인을 요청하지 않고 진행한다.

1. 시작할 때 보드와 관련 Issue를 확인하고 진행 상태를 갱신한다.
2. 범위나 판단이 바뀌면 Issue에 이유와 다음 행동을 기록한다. 제품 결정이 바뀌면 제품 결정 문서에도 반영한다.
3. 중단할 때 현재까지 한 일, 남은 일, 다음 행동과 막힌 이유를 남긴다.
4. 완료할 때 결과와 검증 근거를 연결하고 Issue를 닫은 뒤 Project 상태를 확인한다. PR 병합이나 Issue 종료와 Done의 연동은 보드 자동화 설정을 확인한다.

과거 문서의 미결 항목을 모두 실행 과제로 등록하지 않는다. 지금 필요한 결정과 착수할 일부터 등록하고, 문서 작성 완료와 제품 가설 검증 완료를 구분한다.
