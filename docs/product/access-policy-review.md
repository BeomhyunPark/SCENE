## 확정한 접근 기준

| 사용자 | 조회 범위 | 작업 권한 |
| --- | --- | --- |
| 조직 관리자 | 같은 조직 행사의 전체 정보. 행사 운영진 지정 없이 참가자 정보·연락처·신청 답변·개인별 정산 상세 등 행사 데이터를 조회 | 조회가 행사 수정 권한을 자동 부여하지 않음. 조직·운영진 관리의 상세 절차는 #4·#5에서 검토 |
| 행사 운영진 | 사람별 담당 업무에 맞게 부여한 정보 범위 | 참가자 수정·조 편성·일정·공지·체크인·정산 등의 업무 권한을 사람별로 달리 부여 |
| 그룹 리더 | 자기 조원의 전체 정보와 리더에게 공개된 정보. 연락처·신청 정보도 포함 | 이번 답변은 조회 범위에 대한 결정. 별도 수정·공개·Export 권한을 자동 부여하지 않음 |
| 일반 참가자 | 자기 개인정보와 참가자용 공지·시간표 등 안내 | 운영진·리더용 정보나 다른 사람의 개인정보 접근으로 확대하지 않음. 기존 신청 수정 흐름은 유지 |

사용자는 조직 관리자가 이미 교적 관리 과정에서 정보를 알고 있고 행사 전반을 확인해야 하므로 일부 정보를 별도로 숨길 필요가 없다고 답했다. 조장은 자기 조원을 관리하기 위해 조원의 모든 정보를 알아야 한다고 답했다. 앞선 보고용 요약·개인별 상세 별도 허용안과 조장 연락처 제한안은 채택하지 않는다.

“전체 정보”의 범위는 조직 관리자에게는 같은 조직의 행사, 그룹 리더에게는 자기 조원의 행사 데이터다. 그룹 리더에게 다른 조원 전체 정보나 행사 전체 운영진 정보까지 주는 결정은 아니다. 조회와 수정·공개·Export는 서로 다른 행동이다. 기존 `space_id / event_id / participant_id` 경계를 유지한다.

행정간사·회계간사·담임목사는 조직 관리자 사례이며 직책을 시스템 역할에 자동 매핑하지 않는다. 그룹 리더를 모든 운영진과 동일한 권한으로 취급하지 않는다.

## 정보 구분과 접근 정책

기존 `PUBLIC / INTERNAL / PERSONAL / SENSITIVE / SECURITY` 분류를 유지한다. 이 구분은 정보의 성격과 처리·조회 기록을 설계하기 위한 기준이다. 사용자에게 확정받은 조직 관리자·그룹 리더의 전체 조회 범위를 이 분류만으로 축소하지 않는다.

| 종류 | 예시 | 적용 |
| --- | --- | --- |
| 행사 안내 (`PUBLIC`) | 공개된 일정·장소·공지 | 해당 안내 대상자에게 제공. 익명 인터넷 공개와 구분 |
| 내부 운영정보 (`INTERNAL`) | 준비 업무·편성 초안·정산 업무·내부 운영 메모 | 조직 관리자 조회 및 행사 운영진의 업무 권한에 따름. 일반 참가자에게 자동 제공하지 않음 |
| 개인 식별정보 (`PERSONAL`) | 이름·전화번호·신청 답변·보호자 연락처 | 조직 관리자 전체 조회, 리더의 자기 조원 전체 조회, 운영진의 업무별 범위, 본인의 자기 정보 범위 적용 |
| 특별히 제한할 정보 (`SENSITIVE`) | 건강·돌봄·관계 사유 등 실제 수집 필요가 확인된 정보 | 확정된 조직·자기 조원 조회 범위를 적용하며 그 외 운영진은 업무 권한에 따름. 새로운 수집 항목이나 기능을 확정하지 않음 |
| 보안·접근 기록 (`SECURITY`) | 개인정보 조회·보안·감사 기록 | 기존 기록 접근 정책에 따름. 비밀번호·raw access key·session 원문 제공은 행사 데이터 전체 조회에 포함하지 않음 |

이 문서는 제품 접근 정책을 기록한다. 법률상 정보 분류나 보존 기간을 새로 확정하지 않는다. 개인정보 조회·Export의 기존 기록 기준을 유지한다.

## 권한 없는 화면과 서버 처리 — 확정

사용자는 버튼을 숨겨도 URL 등 다른 방법으로 접근할 수 있으므로 화면과 서버의 권한 판단이 일치해야 한다는 설명에 동의했다.

| 상황 | 화면 | 서버 |
| --- | --- | --- |
| 조회 권한 없음 | 메뉴·정보를 숨김 | 데이터 반환을 거절 |
| 조회 가능·수정 권한 없음 | 읽기 전용 | 변경 요청을 거절 |
| 권한은 있으나 행사 종료 등 업무 조건으로 실행 불가 | 비활성화하고 이유 표시 | 해당 업무 조건을 검사해 실행 거절 |
| 직접 링크 진입·사용 중 권한 회수 | 접근 불가 안내 | 현재 유효한 권한·대상 범위를 검사 |

체크인만 맡은 운영진이 정산 권한을 받지 않았다면 정산 정보는 화면에서 보이지 않고 직접 요청도 거절된다. 반대로 조직 관리자가 전체 조회를 허용받았다면 화면과 서버 모두 그 조회를 허용해야 한다. 실제 적용은 [OWASP의 요청별 권한 검증 기준](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)과 기존 서버 Permission·tenant·resource 소속 검사에 맞춘다.

## 후속 작업과 기술 검토

- #4: Owner 수·권한 부여자·위임·탈퇴 및 책임 이전.
- #5: 조직 생성·가입·초대·승인. 직책과 시스템 역할의 구분을 유지.
- #6: 조 편성 저장·공개와 참가자에게 제공되는 안내 범위.
- #9: Export·보존·삭제·복구. 전체 조회와 별도의 Export·변경 권한을 구분.
- #10: 승인된 정책을 적용한 실제 프로토타입 클릭·접근 상태 검토.

사람별 권한의 저장 schema와 역할 기본값의 결합 규칙, 그룹 리더 identity, 조회 endpoint/DTO와 Notice targeting의 기술 계약은 구현 설계에서 정한다. 고정 Role → Permission Set 기준만으로 이 제품 요구가 해결됐다고 해석하지 않는다. 별도 테이블·endpoint를 이번 제품 정책 검토에서 새로 확정하지 않는다. (2026-10-02 현 결정으로 저장 schema와 결합 규칙을 정했다: role 기본값 + 사람별 `event_user_permissions` GRANT/REVOKE, Event Owner만 부여. [DEC-029](PRODUCT_DECISIONS.md#dec-029--행사-운영진의-업무-권한을-사람별로-달리-부여한다)와 [API Architecture](../architecture/api-architecture-v0.1.md#2026-10-02-개인별-권한-현-결정-dec-029-정합) 참조)

Figma에는 확정 정책과 남은 질문을 주석으로 반영한다. 실제 권한 판정 구현이나 모든 화면의 클릭 QA가 완료됐다고 주장하지 않는다.


## #6 공개본 기준 추가

[조 편성 공개 정책](group-publication-review.md)에 따라 일반 조장의 자기 조 범위는 공개된 편성 기준이다. 작업본에서 이동했다고 일반 조장의 공개 명단이 즉시 바뀌지 않는다. 편성 업무 권한을 가진 조장·운영자의 작업본 접근은 별도로 판정한다. 조직 관리자 전체 조회와 조원 전체 정보 범위는 유지하며 일반 참가자는 자기 공개된 배정만 조회한다. [#7 확정 정책](group-change-recovery-review.md)에 따라 취소자는 재공개를 기다리지 않고 활성 편성·조장 조회에서 즉시 제외한다. 일반 이동은 공개 시 조장 범위를 전환하고 현재 권한 회수는 즉시 적용한다. 과거 배정 기록 보존이 조장의 취소자 조회를 허용하지 않는다.
