## 3. 확장을 염두에 둔 공통 구조

기능을 줄여서 일정을 맞추지 않는다. 대신 아래 구조를 먼저 정하고, 1월에 쓰는 화면은 그 구조의 첫 번째 사용처로 만든다.

1. **행사 안에서 전화번호 하나가 참가자 한 명이다.** 참가자는 이름, 전화번호, 신청할 때 본인이 정한 숫자 6자리로 들어온다. 같은 전화의 재신청과 참가자의 수정은 같은 경로이고, 새 답은 새 revision으로 저장하며 이전 답은 `SUPERSEDED`로 남긴다(`applications.status`에 이미 있는 값). 본인 확인 방식은 갈아 끼울 수 있게 둔다: 지금은 숫자 6자리이고, 나중에 문자 인증이나 참가자 계정으로 바꿀 수 있다.
2. **작업본과 공개본.** 조 편성이 이미 쓰는 방식(작업본 저장, 공개할 때 스냅샷, 버전, 공개 시각, `ALREADY_PUBLISHED`)을 일정표·숙소(식사 순서는 보류, 결정 14)에도 같은 계약 모양으로 쓴다. 테이블은 도메인별로 따로 둔다(범용 배정 테이블을 만들지 않는다는 data-model 원칙 유지). 참가자는 늘 가장 최근 공개본만 본다.
3. **칸 id가 공통 키.** 신청서 설정이 만드는 `opt_d{일차}_{breakfast|lunch|dinner|worship}`를 식수 집계·조 편성판이 이미 같이 쓴다. 식수 현황, 일정표의 식사·집회 항목(보류한 식사 순서도)도 이 id로 잇는다. 나중에 끼니별 체크나 선택 강의 같은 새 칸을 더할 수 있다.
4. **대상(audience).** 공지와 일정 항목은 "누가 보는가"를 갖는다. 1월에는 전체·조장·운영진 세 가지만 쓰고, 저장은 종류와 참조 id의 목록으로 해서 나중에 특정 조·방·역할을 더한다.
5. **참가자 화면은 카드 단위 조회와 갱신 확인.** 카드마다 조회 경로를 따로 두고(`/participant/check-in`, `/participant/group`이 이미 그렇다), 가벼운 `GET /participant/updates`가 카드별 버전만 돌려준다. 화면은 이 값을 30초 안팎으로 확인해 바뀐 카드만 다시 읽는다. 나중에 SSE나 웹 푸시로 바꿔도 카드 계약은 그대로다.
6. **알림은 받는 사람별 목록이다.** 운영자 알림(신청 수정·재신청·취소)과 참가자 알림(새 공지, 일정 변경, 조·숙소 공개. 식사 순서는 보류)을 같은 모양(종류, 가리키는 대상, 시각, 읽음)으로 둔다. 1월에는 화면 안에서만 보이고, 전달 채널(웹 푸시, 알림톡, 문자)은 나중에 이 목록에 붙인다.
7. **체크는 "지점" 단위.** 1월에는 도착 체크인(DEC-071)만 쓴다. 끼니별·집회별 체크는 만들지 않지만, 더할 때는 같은 QR·같은 스캔 화면·같은 재전송 규칙에 칸 id를 붙이면 된다.
8. **행사 유형에 묶지 않는다.** 일정·공지·숙소(보류한 식사 순서도)는 행사가 켜는 기능 영역이다. 지금 브라우저에만 저장하는 "시작한 영역"을 서버로 옮겨 다른 유형의 행사도 필요한 영역만 켠다.
9. **권한 키는 있는 것을 쓴다.** `SCHEDULE_WRITE`, `NOTICE_WRITE`, `ROOM_WRITE`, `CHECKIN_WRITE`, `PARTICIPANT_WRITE`가 이미 있다. 새 키는 꼭 필요할 때만 만든다.
10. **참가자끼리 보는 범위는 "마주치면 알 수 있는 정보"다.** 이름·또래·성별·조·방까지 연다. 연락처와 신청 답은 열지 않는다. 범위는 행사별 스위치로 둔다.

## 4. 작업 트랙과 작업 단위

| 8 | 수련회 조건 | 날짜 미정, 최대 200명, 참가 유형 미정, 와이파이·LTE 가능, 접수대 1~2곳 | J6, J7, J10 |
| 9 | 참가자의 신청 수정 | 참가자가 직접 고치고, 고치면 운영자에게 알림이 간다 | A4~A6, I3 |
| 10 | 이름과 전화번호만으로 들어오면 아는 사람이 남의 신청을 볼 수 있다 | 본인만 아는 숫자 6자리를 함께 검증한다 | A1~A4, A3b, 6.3절 |
| 11 | 조장이 조원의 전화번호를 보나 | 본다. 조원끼리는 보지 않는다 | F1, F2 |
| 12 | 운영자 권한(2026-11-20) | 운영자가 모든 권한을 가져야 편하다. MANAGER에게 전부 준다(OWNER 전용 둘 제외). STAFF는 체크인만 그대로 | I2. 결정 7을 넓힌다 |
| 13 | 숙박하지 않는 사람을 방에 넣을 수 있나(2026-11-20) | 허용하지 않는다 | G1~G5. DEC-085 결정 대기 3을 바꾼다(Follow-up 2026-11-20). 배정한 뒤 숙박을 뺀 사람은 자동으로 빼지 않고 공개할 때 확인받는다(결정 대기 7, 추천안) |
| 14 | 식사 순서(2026-11-20) | 일단 전부 뺀다. 현장에서 관리한다 | 트랙 H 범위 밖. DEC-086 보류(계약 초안은 남김). B3 "다음 식사" 카드, F4의 식사 순서, I5의 "식사" 메뉴를 뺀다. `features.mealOrder`는 유형 기본값으로 켜지지 않는다 |

### 6.2 남은 확인

없다. 수련회 날짜가 정해지면 배포 동결일(J9)을 적는다.

### 6.3 숫자 6자리 본인 확인 (결정 10)

이름과 전화번호는 교회 안에서 서로 아는 정보라 그것만으로는 남의 신청을 볼 수 있다. 그래서 신청할 때 본인이 정한 숫자 6자리를 함께 검증한다. A1에서 아래를 계약으로 적는다.

| 항목 | 안 |
|---|---|
| 정하는 때 | 신청서 끝에서 두 번 넣는다. 필수다 |
| 받지 않는 번호 | 같은 숫자 반복(`000000`), 이어지는 숫자(`123456`), 자기 전화번호에 들어 있는 숫자열 |
| 저장 | 느린 해시로만 저장한다. 응답·로그·CSV·운영자 화면 어디에도 나오지 않는다 |
| 틀렸을 때 | 이름·전화번호·6자리 중 무엇이 틀렸는지 구분하지 않는다. 전화번호별로 연속 5회 틀리면 일정 시간 잠그고, IP별 시도도 제한한다 |
| 잊었을 때 | 운영자가 초기화하면 임시 번호가 한 번 보인다. 참가자는 그 번호로 들어와 새 번호를 정한다(A3b) |
| 같은 전화의 재신청 | 6자리가 맞으면 수정으로 덮어쓴다. 틀리면 이미 신청이 있다고만 안내한다 |
| 도착 체크인 | 6자리와 상관없다. QR이 없어도 접수대에서 이름·전화 끝자리로 체크인한다 |
| 조장 | 조장도 참가자라 같은 방식으로 들어온다. 조원의 전화번호를 봐도 6자리를 모르면 조원으로 들어갈 수 없다 |

남는 위험: 6자리는 경우의 수가 백만이라 잠금과 시도 제한이 있어야만 안전하다. 6자리를 남에게 알려 준 경우는 막지 못하고, 그때는 수정 이력과 운영자 알림(A4, A6)으로 되돌린다.

## 7. 이번 범위 밖

구조는 열어 두고 만들지 않는다.

- 참가비 납부 확인(#230 결정)
- 끼니별·집회별 QR 체크(결정 1)
- 문자·알림톡 발송, 참가자 계정, 문자 인증
- 정원·대기
- 차량 배정과 카풀 짝 맞추기
- 조·숙소 자동 편성(제품 정의가 알고리즘 편성을 두지 않는다)
- 식사 순서(트랙 H, 결정 14). 현장에서 관리한다. 정책·계약 초안(DEC-086)은 남겨 둔다
- 숙박하지 않는 사람의 방 배정(결정 13)
- 조직 달력, 연동 메뉴
- 완전 오프라인 체크인 대기열
