# 조직 생성·가입·초대 검토 결과

- 검토일: 2026-09-30
- 상태: 제품 정책 반영. 초대 기간·기술 계약과 실제 화면 검토는 후속.
- 소스: [이슈 #5 사용자 답변](https://github.com/BeomhyunPark/SCENE/issues/5#issuecomment-5902896850)

## 조직 생성

SCENE 운영계정 가입·이메일 인증 → 조직 검색 → 기존 조직이 없거나 중복 후보가 다른 조직임을 확인 → 조직 생성 → 생성자가 최초 조직 Owner가 된다. 생성 시 조직을 생성·운영할 권한이 있음을 확인받는다. 초기 흐름에 별도 SCENE 승인·교회 증명서·사업자등록증 제출을 추가하지 않는다.

Owner와 결제 담당자는 구분하고 Owner는 이후 복수 가능하다. 이 흐름이 교적관리 기능을 새로 포함하는 것은 아니다.

## 가입 요청과 조직 초대

| 경로 | 시작 | 처리 | 결과 |
| --- | --- | --- | --- |
| 조직 검색·가입 요청 | 사용자 | 조직 Owner 승인 또는 거절. 대기 중 사용자가 취소 가능 | 승인 후 MEMBER |
| 대상자 조직 초대 | 조직 Owner | 대상자가 수락. 추가 Owner 승인 없음 | 수락 후 MEMBER |
| 행사 초대 | 해당 행사의 운영자 관리 권한자 | 대상자가 수락. 조직 소속과 행사 접근은 구분 | 해당 행사 접근만 부여. 조직 가입은 별도 |

초기 조직 가입 승인·거절은 조직 Owner가 담당한다. 행사 Owner라는 이유만으로 조직 가입 승인권을 주지 않는다. 조직 초대는 대상 이메일·조직·부여할 기본 접근 범위·만료 시각·1회 사용 토큰을 가진다. 전달 가능한 무제한 공개 가입 링크로 사용하지 않고 의도한 계정이 수락하도록 한다.

대기 중 사용자는 해당 조직에 대해 요청 상태 확인·취소만 가능하며 조직 내부 행사·참가자·문서·운영 데이터는 보지 못한다. 다른 조직 검색·가입, 새 조직 생성은 별도로 조건을 만족할 때 가능하다. PENDING은 MEMBER가 아니다.

거절 결과는 상세 사유를 반드시 공개하지 않고 “가입 요청이 승인되지 않았습니다”로 안내할 수 있다. 재신청은 허용한다.

## 중복·잘못된 요청·초대 만료

조직명·지역과 필요시 교단·설명 등 최소 비교 정보로 중복 후보를 보여준다. 기존 조직 가입 요청 또는 다른 조직임을 확인하고 새로 만들기를 선택할 수 있다. 같은 이름만으로 조직 생성을 차단하지 않는다.

중복 조직의 자동 병합은 지원하지 않는다. 실제 중복은 별도 신고·운영지원 확인·유지 조직 선택·필요한 관계/행사 이전·중복 조직 보관/종료 절차로 검토한다. 상세 이전·복구 계약은 여기서 확정하지 않는다.

잘못된 대기 요청은 사용자가 취소하거나 Owner가 거절한다. 승인 이후에는 일반 Membership 제거·책임 인계 정책을 적용한다.

초대는 수락·취소·만료를 구분하고 보낸 권한자가 수락 전 취소할 수 있다. 만료된 초대는 다시 초대한다. 사용자 답변의 **7일은 초기 만료 기간 제안값**이다. 최종 요약에는 기간이 특정되지 않았으므로 정확한 TTL·재전송 시 기존 토큰 처리·수락과 취소의 동시성은 상세 계약에서 확정한다. 7일을 이미 확정한 상수로 구현하지 않는다.

## 조직 소속과 행사 접근

조직 Membership과 행사 Role은 별개다. 조직 Member에게 행사 Role을 부여할 수 있고 맡은 행사가 없는 Member도 가능하다. 임시 스태프·외부 협력자는 **조직 Membership 없이 특정 행사만 운영**할 수 있다.

행사 초대의 기본 결과는 해당 행사 접근이다. 조직 가입을 자동 실행하지 않는다. 조직에도 가입시키는 흐름은 별도 조직 가입·초대 정책을 따르며 행사 Owner의 권한으로 조직 가입을 승인하지 않는다.

외부 행사 운영자가 행사 접근을 받더라도 조직 내부 화면·다른 행사·조직 구성원 관리까지 열리지 않는다. 서버는 해당 행사의 운영자 관계와 업무 권한을 확인해야 한다. 조직을 공유하는지 확인하는 것만으로 권한을 판정할 수 없다.

## 기존 기술 기준의 변경

기존 `user → member → event_user` 필수 경로와 모든 행사 운영자 추가에 `memberId`를 요구하는 기준은 외부 행사 협력자 요구와 충돌한다. 조직 Member 경로는 유지할 수 있지만 행사 운영자의 유일한 경로로 강제하지 않는다.

다음 상세는 후속 설계에서 정한다.

- 운영계정 ↔ 행사 운영자 관계와 조직 Membership의 선택적 연결 방식
- Member와 행사 전용 운영자의 초대·역할 부여·회수·조회 계약
- 조직 탈퇴가 별도 행사 접근에 미치는 영향과 잔여 책임 검사
- 행사 Owner·그룹 리더 후보의 자격, 조직·행사별 권한 상한
- 초대 토큰 대상 검증·재전송·1회 소비·동시성 및 정확한 만료 기간

기존 Event tenant anchor, resource 소속, 서버 Permission 검사와 사용자·Participant 구분은 유지한다. 테이블·FK·nullable·endpoint를 이번 제품 답변만으로 정하지 않는다.

## Figma·후속 검토

P14·START HERE 정책 주석에 생성자 Owner, 가입 승인/초대 수락, 대기 사용자 경계와 행사 전용 협력자 방향을 반영한다. 조직 생성 중복 후보, 대상 이메일 일치, 초대 수락·취소·만료, 재신청, 조직 소속 없이 행사 진입 경로는 #10 실제 프로토타입 검토에 포함한다. 문서·주석 반영이 기능 구현 완료를 뜻하지 않는다.
